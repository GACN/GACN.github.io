# Pascal AI Runtime：老显卡运行现代 AI 的实战记录

> 用一张 NVIDIA TITAN X Pascal 12GB，在 Windows 10 上研究 SM61 老架构运行现代 AI 图像/视频模型的可行性。
>
> 这不是“老显卡秒变新显卡”的营销帖，而是一份按实验记录整理的教程：哪些跑通了、哪些真的变快了、哪些只是微基准、哪些没有完成，都明确区分。

- **主机显卡**：NVIDIA TITAN X Pascal 12GB
- **GPU 架构**：Pascal，Compute Capability 6.1（SM61）
- **系统**：Windows 10
- **系统内存**：32GB（2 × 16GB）
- **模型盘**：SATA SSD
- **主要实验**：FreeVideo-Pascal 分支、MiniMax H3 视频生成、DP4A / INT8 Linear
- **记录状态**：2026-11-23；后续实验已暂停，ComfyUI 计划卸载

## 先看结论

这张 TITAN X Pascal 确实完成了 448×320、243 帧、约 10.125 秒的视频生成：

- 243 帧，24 FPS，双轮 8+3 步
- 引擎权威耗时 1509.3 秒，约 **25 分 09 秒**
- 没有 CUDA OOM，没有自动降低分辨率或步数
- 生成画面可连续播放，但输出属于低码率预览级，不是成片级

我们还验证了 SM61 上的 DP4A INT8 整数矩阵计算，并把 INT8 分支接入独立的 FreeVideo-Pascal 实验引擎：

- 39 帧测试中，QKV INT8 的引擎总耗时从 396.90 秒降到 357.13 秒，观测到约 **10.0%** 的端到端改善
- 但 PSNR 33.55 dB、SSIM 0.9527，未达到预先设定的 PSNR ≥ 35 dB、SSIM ≥ 0.98
- 因此没有把该版本用于 243 帧长视频测试

**最诚实的结论：硬件兼容、10 秒视频生成、DP4A 微基准和 INT8 集成均有实测成果；但目前没有一个同时满足“10 秒视频更快且画质达标”的 INT8 成品方案。**

## 2. 先理解 Pascal：SM61、DP4A 和 Tensor Core

### 2.1 Pascal 不等于“不能跑 INT8”

TITAN X Pascal 的 Compute Capability 是 6.1。

它没有 Tensor Core，但 Pascal GP10x 系列支持 DP4A 整数点积指令。DP4A 的核心思想是：一次指令对四组 8-bit 整数进行乘法并累加到 32-bit 整数结果。

简化表达：

~~~text
result = a0*b0 + a1*b1 + a2*b2 + a3*b3 + accumulator
~~~

因此，Pascal 可以执行某些 INT8 点积计算；但这不等于所有现代 AI 框架都自动为它选择了高效 INT8 路径。

### 2.2 Tensor Core 与 DP4A 不是一回事

- **Tensor Core**：专用矩阵计算单元，出现在更新的 NVIDIA GPU 架构中。
- **DP4A**：普通 CUDA 核心可执行的整数点积指令，不是 Tensor Core。
- **SM61**：Pascal 的计算能力标识。
- **INT8 权重文件**：只代表存储格式，不能证明运行时真的在做 INT8 乘法。

### 2.3 本次发现的关键问题

FreeVideo-Pascal 原始 INT8 路径中，SM61 因为低于 SM80，进入了 PyTorch 反量化路径：

~~~text
INT8 values + scales
        |
        v
convert to FP32
        |
        v
FP32 GEMM
        |
        v
output
~~~

因此，INT8 文件主要节省权重存储和读取量，并没有自动带来 INT8 矩阵计算的吞吐量收益。

在当时的 Windows 环境中，Triton 导入还遇到缺失问题。原引擎没有提供可直接使用的 Pascal DP4A Linear 路径。

## 3. 实验路线：先基线，再找瓶颈

本次实验不是一开始就修改模型，而是分阶段进行：

1. 让原始 FreeVideo-Pascal 环境成功运行。
2. 固定提示词、Seed、分辨率和步数，建立短视频基线。
3. 验证长视频是否能完整运行。
4. 通过 engine.json、GPU 监控和系统监控分析瓶颈。
5. 单独测试磁盘读取线程和解码预读。
6. 建立 DP4A 独立 GEMM 微基准。
7. 捕获真实 H3 激活，离线回放量化误差。
8. 在独立实验分支中集成 INT8 Linear。
9. 用 PSNR、SSIM、LPIPS 检查画质。
10. 画质未达标时停止扩展，不用未验证版本跑长视频。

### 计时口径必须统一

本项目遇到过三种时间：

- **request_seconds**：引擎内部记录的请求耗时，作为总耗时主口径。
- **脚本墙钟时间**：提交请求到取回文件的时间，包含轮询、复制等开销。
- **阶段计时器求和**：可能因为后台预读和外层包装计时而重复计算。

因此：

**总耗时只比较 request_seconds；阶段时间逐项分析，不把重叠阶段简单相加。**

不同实验的缓存状态、模型加载方式和计时口径不同，不能把所有数字直接横向比较。

### 4.3 Token 数量不是按像素随意估算

本次引擎实际记录：

~~~text
frames        = 243
latent_frames = 72
video_tokens  = 10080
~~~

对应关系：

~~~text
每个 latent frame = 140 tokens
72 × 140 = 10080 tokens
~~~

另一条续接实验中：

~~~text
latent_frames = 22
video_tokens  = 3080
prefix_tokens = 980
~~~

续接前缀为 7 个 latent frames × 140 tokens = 980 tokens，占该段 3080 tokens 的约 31.8%。

### 4.4 Latent Continuation 已验证

这次续接不是把两段独立 MP4 拼在一起。

引擎通过 Transformer forward pre-hook 注入上一段 latent 前缀，并且第二段目录中保存了 continuation-source.safetensors，包含 video_hi、video_lo 和 audio latent。

因此，至少在这条实验路径中，续接使用的是真正的 latent 上下文。

注意：现有 runtime.py 参数过滤补丁曾静默丢弃 stop_check 等不兼容参数，导致 early-stop / 中途预览停止能力失效。续接路径不依赖这些参数，但该副作用需要保留在维护记录中。

### 5.1 10 秒视频阶段时间

243 帧实验的阶段记录：

| 阶段 | 记录时间 |
|---|---:|
| 模型装载 | 138.1 秒 |
| Sampling | 1175.8 秒 |
| VAE 装载 | 45.2 秒 |

| Audio Decode | 5.6 秒 |

采样占 request_seconds 约 77.9%，是最主要的计算时间。

采样平均约 4.84 秒/帧；端到端吞吐量约 0.161 FPS。视频播放帧率是 24 FPS，但生成速度不是实时的。

### 5.2 GPU 与系统资源

243 帧压力测试的系统采样：

| 指标 | 记录 |
|---|---:|
| 可用物理内存均值 | 5710 MB |
| 可用物理内存最低 | 2674 MB |
| 提交量峰值 | 35.8 GB |
| Page Reads/sec 峰值 | 6.97 |
| Page Writes/sec | 0 |
| 页面文件使用率峰值 | 24.4% |
| 磁盘队列均值 | 0.01 |
| 磁盘活动均值 | 0.38% |
| CPU 利用率均值 | 15.4% |

显存记录存在不同监控口径：

- 引擎/监控记录峰值约 11.16 / 12.29 GB。
- 运行时曾看到约 11.9 / 12 GB。
- PyTorch peak allocated 约 7.37 GiB。

这些值不是同一个统计指标，不能混为一谈。

本次没有证据显示持续磁盘等待或页面文件写入抖动。对这条 10 秒工作流而言，真正的主要限制是 GPU 采样计算时间。

### 5.3 系统内存升级判断

本机 32GB 内存能够完成 243 帧任务。虽然提交量超过物理内存容量，但页面文件使用率约 24.4%，Page Writes/sec 全程为 0。

因此：

- 不能说 32GB 内存完全充裕。
- 也不能说这次任务因为内存不足而明显变慢。
- 64GB 对多任务、更大模型常驻和更大分辨率可能有帮助。
- 但仅为了当前 10 秒基准，不足以证明必须立即升级。

### 5.4 SATA SSD 与读线程测试

模型盘冷读速度曾测得约 177 MB/s。

三组单变量测试：

| 配置 | 总时长（脚本墙钟） | block_bind |
|---|---:|---:|
| 冷态默认 | 391.1 秒 | 基准 |
| READ_THREADS=8 | 391.3 秒 | 105.2 秒 |
| DECODE_READ_AHEAD=off | 411.0 秒 | 107.2 秒 |

引擎 request_seconds 的记录口径另为：RT8 组 370.0 秒，关闭预读组 388.0 秒。

结论：

- READ_THREADS 从 4 提到 8 没有收益，反而增加绑定耗时。
- 关闭解码预读更慢。
- 保持默认读取线程和自动预读。
- NVMe 迁移对照尚未完成，不能提前声称能缩短到某个具体时间。

## 6. INT8 / DP4A 优化研究

### 6.1 第一轮：独立 GEMM 微基准

在 CUDA Toolkit 12.8 + MSVC 14.44 环境中，使用 sm_61 编译 DP4A 测试。

矩阵测试记录：

| M×K×N | FP32 cuBLAS | INT8→FP32 路径 | INT8 DP4A | 相对 FP32 |
|---|---:|---:|---:|---:|
| 10080×5376×5376 | 7515 | 7904 | 23813 | 3.17× |
| 10080×5376×14336 | 7271 | 7649 | 23464 | 3.23× |
| 1024×5376×5376 | 10264 | 8930 | 26026 | 2.54× |
| 1024×5376×14336 | 9402 | 8632 | 22866 | 2.43× |

以上数值沿用当时微基准报告的吞吐量记录。不同精度的运算量计数口径必须一致后才能做严格的 TOPS/GFLOPS 对比。

正确性检查：
- 独立 CUDA 内核编译成功。
- PTX 中出现 dp4a.s32.s32。
- 共记录 14 处。
- Torch Profiler 观察到 cuBLAS Kernel：maxwell_igemm_int8_128x128_ldg4_nn。
- 随机 256 行整数点积与 Host 复算一致。
- INT32 累加峰值约 18.2 万，远低于 2^31。

没有安装 cuobjdump / nvdisasm，因此没有完成 SASS 反汇编。现有证据支持 SM61 实际使用整数 IGEMM 路径，但不能声称已经完成机器码级的完整审计。

### 6.2 为什么独立测试 3 倍，不代表视频整体 3 倍

独立 GEMM 只测一个矩阵计算内核。

完整视频生成还包括：
- 激活量化
- 权重流式读取
- 模型调度
- Kernel Launch
- 输出 Scale 还原
- Attention
- VAE
- 音视频编码

因此，独立 GEMM 的 2.43～3.23 倍不能直接外推为整个 H3 的加速倍数。

## 7. 真实激活与量化误差

### 7.1 真实激活捕获

在独立进程中加载引擎，使用 forward_pre_hook 只读捕获数据。

本次捕获：
- Transformer 层：0、16、32、49
- Linear 类型：6 种
- 采样步骤：0 和 7
- 共 48 条记录
- 每条保存前 128 个 Token 的 fp16 切片

- 磁盘样本约 43 MB

捕获需要独占 GPU。ComfyUI 服务仍在运行时曾发生 CUDA OOM；停止服务后成功完成。

### 7.2 真实激活分布

|---|---:|---:|---:|---:|

| ff_proj | 5376 | 87.5 | 4.2 | 0.43 |
| ff_down | 14336 | 8096 | 2064 | 69.5 |

MLP Down 的动态范围远高于其他模块。

### 7.3 真实激活回放

| 模块 | 平均 Relative RMSE | 量化为 0 的比例 |
|---|---:|---:|
| to_out | 1.840% | 约 4.5% |

| SSIM | 0.9502 | 0.9527 |
| LPIPS mean（AlexNet） | 0.0699 | 0.0664 |

预设验收门槛：
- PSNR ≥ 35 dB
- SSIM ≥ 0.98

QKV 仍然未通过 PSNR 和 SSIM 验收。LPIPS 0.0664 表示存在可感知差异，不是无损结果。

因此：
- 没有执行 243 帧 INT8 测试。
- 没有宣称 10 秒视频获得 10% 加速。
- 没有宣称 INT8 版本可以替代原始 FP32 生产路径。

## 9. 踩坑与经验

1. **不要把 INT8 权重等同于 INT8 计算。** 必须检查实际 Kernel 路径。
2. **不要把独立 GEMM 加速倍数等同于端到端加速。**
3. **不要混用 request_seconds、脚本墙钟和阶段计时器求和。**
4. **真实激活比合成激活更重要。** 合成数据上的低误差不保证真实模型输出质量。
5. **不要随意截断离群值。** P99.9 截断曾让相对误差从约 4.2% 恶化到 14.1%。
6. **不要在 ComfyUI 服务运行时同时进行激活捕获。** 本机曾发生 CUDA OOM。
7. **不要为了通过指标而事后降低画质门槛。**
8. **先做 39 帧验证，再做 243 帧验证。**
9. **长视频成功生成不等于成片质量合格。** 分辨率、码率、压缩和模型细节都要检查。
10. **每次实验都保留原始 FP32 回退路径。**

### 最终判断

本项目证明了 Pascal SM61 并非完全不能参与现代 AI 推理。通过合适的软件路径，可以运行视频生成模型，也能使用 DP4A 进行真正的 INT8 整数计算。

但对于本次 TITAN X Pascal + FreeVideo-Pascal + MiniMax H3 实验：

- 10 秒视频生成成功，约 25 分钟。
- INT8 QKV 在 39 帧测试中观察到约 10% 总耗时改善。
- 该 INT8 版本没有达到预设画质标准。
- 243 帧 INT8 优化尚未验证。
- 因此当前最可靠的长视频基准仍是原始 FP32 路径。

**如果主要目标是低成本、快速、稳定地生成高质量视频，这张老显卡并不适合承担主力视频生成工作。它更适合游戏、传统 GPU 任务，以及学习 CUDA、模型量化和推理优化。**

本记录后续停止主动扩展 ComfyUI 实验，保留为一次完整的老架构 AI 优化研究案例。
